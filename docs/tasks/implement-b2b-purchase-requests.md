### Alternatives and recommended lifecycle

- Immediate create-and-export is smaller but removes the reviewed approval boundary; do not choose it for this proposal.
- Recommended: client creates pending; admin approves or rejects; admin/warehouse explicitly fulfills an approved request in full. Creation and approval never reserve/decrement stock. Fulfillment may fail if availability changed; keep approved and let staff retry deliberately.
- Reservations/partial receipt are more involved and would change inventory-position semantics; defer rather than silently adding them.

| Action | Role | Allowed result | Stock effects |
| --- | --- | --- | --- |
| Create | client only | new pending request owned by current actor | none, even when stock is insufficient |
| Read list/detail | client owner; admin/warehouse all | current persisted request and supported history | none |
| Approve | admin | pending -> approved | none |
| Reject, nonblank reason | admin | pending -> rejected | none |
| Fulfill, explicit confirmation | admin/warehouse | approved -> fulfilled | one complete outbound at the selected warehouse |

No on-behalf creation by staff, approvals by warehouse, cancellation, arbitrary status patch, quantity change or fallback warehouse is proposed. Deny anonymous/inactive callers under current auth policy. Client read predicates must be enforced in repository/service queries, including filtered totals and by-ID access; unowned detail returns404. An authorized-role action rejection returns403 before disclosing target existence. No frontend check substitutes for authorization.

Explicit new permission proposal: purchase_request:read for all three roles with client owner scoping; purchase_request:create for client; purchase_request:review for admin; purchase_request:fulfill for admin/warehouse. Add only those grants. Preserve every existing Permission/PERMISSION_ROLES entry and all old route-action assertions. Owner ID always comes from the authenticated user, never a submitted field/filter.

### Publication, inactive products and legacy records

- Recommended compatibility policy: preserve current authenticated-client access to actual product/warehouse/stock APIs and quantities. For new B2B requests, every existing warehouse and active product currently readable through those APIs is requestable. No public anonymous stock access or extra warehouse/customer assignment is introduced. If quantity privacy or tenant-specific catalog/warehouses are required, stop for a reviewed amendment before implementation; this proposal does not claim privacy the current backend lacks.
- New create/approve/fulfill actions require the referenced product to be active; missing product/warehouse is404, inactive product is409 PRODUCT_NOT_REQUESTABLE. This is a proposed B2B admission policy, not a change to old ordinary outbound or M3 inactive-product transfer behavior. A committed create/decision/fulfillment replay returns original persisted effects without rerunning stock/active-product business preconditions, but always after current authentication/authorization.
- Reuse the existing PurchaseRequest table and four statuses. Add a one-to-one PurchaseRequestWorkflow sidecar for API-managed requests; no competing second request entity. Existing records without a workflow are visible to their authorized reader but read-only, with a Vietnamese legacy-history notice. Do not infer that an old fulfilled row has a linked real outbound; its fulfillment metadata stays unknown/null. Mutating a legacy row returns409 LEGACY_PURCHASE_REQUEST_READ_ONLY, without stock changes.
- Sidecar rather than mandatory new base columns preserves existing legacy rows/fixtures and avoids inventing history. Cross-table owner/status/quantity/leg parity is a tested service invariant; do not claim simple foreign keys prove all of it.

- Proposed additive revision20261019_0004, parent20261017_0003, file alembic/versions/20261019_0004_purchase_requests.py. Do not retry domain/validation/permission failures. Same creation key or same request/action recovers a committed result after loss; no universal cross-new-key guarantee. Clients never automatically retry POSTs.
