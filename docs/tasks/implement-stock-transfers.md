### Transfer model, quantity and provenance

- Use an immediate atomic model. One successful transfer subtracts quantity from the source and adds it to the destination at one commit; no pending/in-transit business state or fake arrival time.
- TransferCreate has strict positive integer source_warehouse_id, destination_warehouse_id and product_id; quantity is a strict integer in 1..2_147_483_647, excluding booleans/fractions/coercion. IDs use the same positive PostgreSQL INTEGER bound. Warehouses must differ. reference is optional <=120 characters; note optional <=2000. Trim optional text and normalize blank to null. Forbid unknown fields, including client-supplied actor/status/purpose/link IDs.
- Engineering proposal for human approval: an existing product with is_active=false may still be transferred if source stock suffices, matching the existing inbound/outbound existence check and allowing remaining stock to move. Do not change that flag, invent PRODUCT_INACTIVE rejection, hide inactive products from transfer choices or imply new sale eligibility. Show Ngừng hoạt động beside such a product in the selector/confirmation/detail. Pin both active and inactive transfers and insufficient inactive-product stock in the tests.
- StockTransfer in app/models/domain.py uses table stock_transfers: integer id; source_warehouse_id, destination_warehouse_id, product_id, created_by_id RESTRICT foreign keys; quantity; reference/note; timezone-aware created_at; UUID idempotency_key, 64-character request_fingerprint; source_quantity_before/after and destination_quantity_before/after; nonnull unique outbound_id, inbound_id, outbound_transaction_id and inbound_transaction_id RESTRICT foreign keys. Unique(created_by_id,idempotency_key), distinct warehouses and bounded/nonnegative balance checks. ### Idempotency, locking and failures

- POST requires Idempotency-Key containing one UUID, scoped to authenticated actor and this operation; missing/malformed =>422 REQUEST_VALIDATION_ERROR associated with the header. Store no bearer token. Fingerprint SHA256 of sorted compact JSON from the normalized validated payload, including optional null text. Same key/body/actor replays the original persisted TransferResponse after authorization, even if stock later changes. Different body with that actor/key =>409 IDEMPOTENCY_KEY_CONFLICT with no effects. Different actors may use the same UUID independently. Retain keys with transfer records; no expiry/job/cleanup.
- At the start of each attempt, acquire PostgreSQL transaction-scoped advisory lock for the actor/UUID before any stock lock, then read an existing transfer. Define the signed64-bit lock identifier by domain-separated SHA256 of operation name, actor ID and canonical UUID; take the first8 bytes as a signed big-endian integer. Hash collisions serialize unrelated requests but do not define equality; the exact unique key remains authoritative. No Python hash(), process-local lock or lock held beyond the DB transaction.
- For a new transfer validate product/warehouses, then process the two (warehouse_id,product_id) keys in ascending tuple order. For each key use the existing conflict-safe zero-row insertion and SELECT FOR UPDATE before proceeding to the next key. Read fresh locked balances, require source>=quantity and destination<=MAX_STOCK_QUANTITY-quantity. Missing source behaves as insufficient stock; a speculative zero row must roll back on rejection. The common ordering covers opposite transfers and first-destination creation, including races with ordinary inbound/outbound.
- Use flush-only persistence primitives in one Session; no nested call to the existing committing create_inbound/create_outbound, no repository commit, savepoint pretending to undo an already committed leg or compensating write. Populate both movements/transactions, transfer snapshots and both provenance sidecars, then commit once. Any required-row/flush/commit failure rolls back every effect. A successful response means persisted linked state, not a temporary balance preview.
- Engineering retry proposal: at most3 complete attempts only for SQLSTATE 40P01 or40001, rollback/expire state and reacquire idempotency/stock locks on every attempt. SET LOCAL lock_timeout='3s' per attempt;55P03 or retry exhaustion =>503 TRANSFER_RETRY_REQUIRED, Retry-After:1, no raw DB diagnostics. Do not retry validation/domain/permission errors. A connection loss around commit is ambiguous: report a safe retry-required error, never claim rollback was certainly observed; the same actor/key recovers the committed record or executes once. No automatic browser POST retry.
- Domain failures:404 PRODUCT_NOT_FOUND/WAREHOUSE_NOT_FOUND/TRANSFER_NOT_FOUND,409 INSUFFICIENT_STOCK/STOCK_QUANTITY_LIMIT_EXCEEDED/IDEMPOTENCY_KEY_CONFLICT,422 REQUEST_VALIDATION_ERROR; existing401/403 policy unchanged. Old stock endpoint errors stay unchanged. After terminal rollback a key is unconsumed and may be explicitly retried; no partial pending transfer record is exposed.
