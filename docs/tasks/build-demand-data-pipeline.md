### Approach and deliverables

Recommended: offline batch pipeline with typed normalization and explicit admission metadata, then validated immutable local bundles. This makes data semantics/test fixtures reviewable without adding an upload service, model-training job or dashboard. Direct mutable production-table import is rejected for this milestone; a notebook-only transformation is insufficient as the reproducible consumer boundary.

Inputs are an admitted source manifest, explicit catalog/warehouse/unit mappings, coverage/lifecycle evidence, normalized events and, where available, availability evidence. Operational extraction is a bounded read-only adapter using an explicitly selected connection, coherent snapshot and read-only transaction; it must never fall back to a development DATABASE_URL or treat the demo database as research input. Connection values stay process-local, not CLI logs, output files or committed environment files. Database admission/extraction is separately authorized before use.

Support two explicitly declared input representations: movement events and source daily observations. Events have positive integral quantities; a source daily observation may have a nonnegative integral fulfilled quantity, including a genuine observed zero, only with its declared date/unit/coverage semantics. A null/unknown or partial day remains unknown/partial, not zero. Do not synthesize fake movements or event timestamps from a daily total. External sales/order/net-return columns are not automatically equivalent to gross fulfilled quantity; an incompatible target definition fails admission. Exact tagged schemas and canonical output names are fixed by the later plan.

Each dataset version selects one authoritative source snapshot/namespace and one declared target/channel. Operational M4 managed B2B fulfillment is that channel only, not all warehouse demand or all sales. External research series are separate versions, never automatically unioned with operational records. Multiple files of the same snapshot may be processed with shared stable identities, but two exports/editions or event and aggregate representations of the same series/period cannot both contribute. Reject overlapping/ambiguous input selections; do not resolve overlap by guessing, namespace changes, summing, or silently preferring a source. A future cross-source fusion needs an explicitly reviewed equivalence/precedence design, not this default.

Outputs are a versioned manifest, canonical normalized events/daily observations and an aggregate validation/quality report. Raw inputs and produced bundles remain outside Git in a specifically approved ignored artifact root; .gitignore currently has no dedicated demand-data artifact rule. That rule/path must be included in the later approved allowlist before any artifact is written. Tests use small privacy-safe synthetic fixtures and temporary output directories.

### Event identity, classification and validation

- Identify events by declared source namespace plus stable source event ID, not SKU/date/quantity alone; two real equal-quantity movements must not collapse. Exact repeated identity/payload is counted once with duplicate accounting. Same identity with conflicting payload is a validation conflict, never last-write-wins. Changing source/config is an explicit new version, not an overwrite.
- Validate declared schema/encoding/required fields, known mapped SKU and warehouse, timezone-aware timestamp, positive integral event quantity and consistent supported units. Reject booleans/fractions/coercion, invalid dates, missing identity and unknown mappings; do not create catalog/warehouse records automatically. Normalized daily sums must not silently overflow or mix units. Exact integer bounds/CSV schema/error codes are frozen in the detailed plan.
- Count customer fulfillment once using authoritative M4 workflow/outbound/transaction linkage. Do not also count the request row as a second demand event. Pending/approved/rejected requests are not fulfilled demand and never incoming supply. If request-intent quantities are retained for future analysis, keep them in a separately labeled series, not this target.
- Exclude transfer_in/transfer_out and standard_inbound from fulfilled-demand targets; retain category/count evidence in quality reporting. legacy_unknown and standard_outbound are unclassified for demand unless an admitted source classification explicitly establishes meaning. Never classify from note/reference text or guess customer/supplier identity.
- Returns, corrections, adjustments, cancellations and test/demo events require explicit source labels and separate exclusion/quality accounting; do not infer them from quantity sign or subtract them from gross fulfillment. Missing classification is unknown/quarantined, not a demand label. Source-level fixture/demo admission overrides any movement purpose, so synthetic M4 fulfillment is still synthetic.
- Rejection reports contain safe row/event references, stable reason codes and counts, not complete raw records, notes, names, emails, bearer/connection values or secrets. Data checksums are lineage/integrity identifiers, not a claim of anonymization.

Default publication is strict: malformed/invalid potentially target-contributing rows, identity conflicts, unknown mappings/units, ambiguous overlap, missing required temporal evidence or a broken source/coverage contract fail the whole attempted dataset bundle. They produce a safe validation report only, not a successful dataset manifest or partly accepted training target. Exact duplicates and explicitly valid excluded movement classes are accounting categories, not malformed rejected rows; they need not fail a valid bundle. Unknown-purpose records may be excluded only when the admitted target/channel proves they are outside it. If they could belong to the selected target, the affected coverage is unknown and a complete/zero daily target cannot be published. No tolerance threshold, lossy quarantine-to-success or silent drop is enabled by default; a permissive variant requires reviewed scope/policy approval.

### Daily observations, missingness and availability

Proposed daily key: source/dataset version, product identity, warehouse identity, business date and unit. Default engineering recommendation is declared IANA Asia/Ho_Chi_Minh, never the host's implicit timezone; preserve original aware instants and the conversion rule. Detailed plan pins day/window/cutoff inclusivity, complete-day handling and boundary tests. This is a proposal, not a universal business timezone assumption.

Preserve recognized positive fulfillment counts even when daily observation coverage is partial, but label them partial/lower-bound and exclude them from a fully observed target unless a reviewed consumer policy accepts that class. An absent event is zero only when complete observation/operating-period evidence supports it. Otherwise quantity/observation remains unknown, not forward-filled or silently zero-filled. No product/warehouse Cartesian grid outside an explicitly admitted lifecycle/coverage window.

Current is_active, created_at and unit alone cannot prove historical activity, discontinuation, sale eligibility or historic unit conversion. Use admitted effective-dated mappings/lifecycle evidence; otherwise declare unknown/limited history and block incompatible aggregation/features. New/inactive SKU periods are flagged instead of invented pre-launch demand.

Separate availability evidence from demand-censoring risk. Proposed availability evidence records unknown, an observed stockout interval, or adequately covered positive availability, with source/coverage limitations. Proposed risk values are unknown, potential and not_indicated. A verified stockout within the relevant period implies potential constraint on fulfilled demand, not proof that customers actually lost demand. not_indicated requires complete target observation and adequate positive-availability coverage; it is not a universal proof of unconstrained demand. Missing either kind of coverage yields unknown. Current stock, no orders, a failed fulfillment or one before/after snapshot cannot establish day-long coverage. No confirmed lost-demand quantity or overloaded confirmed/uncensored flag is inferred, and no lost-demand estimation/imputation is introduced. Exact field names, evidence scope and interval-boundary rules are pinned in the detailed plan.

### Cutoff, determinism and safe output

Separate event occurrence from when information became available. For the proposed default as-of dataset, event/date window and available-at instant, or a documented conservative available-at upper bound, must both meet the cutoff. Unknown required availability time is a validation failure for this dataset, not a successful as-of export merely labeled temporal-safety unknown. Retain only safe diagnostic/quality evidence for the failed attempt; no downstream-consumable success manifest is published. A source adapter may derive an availability bound only from an admitted documented recording/collection policy; never assume event time equals information availability or treat today's extraction as proof it was available before an old cutoff. Future records and after-cutoff corrections/current-state hindsight must not leak. No future outcome-derived labels/preprocessing/imputation or randomly split research evaluation is introduced.

Version identity derives from canonical admitted inputs/checksums, schema/rules/classification/mapping/coverage/timezone/cutoff and relevant software version. Stable ordering, UTF-8/canonical JSON/CSV formatting and no run-clock-dependent content in versioned semantic artifacts must produce the same version/hash/results for identical input/config. Run timing may be separate execution metadata, not a reason to silently create a different dataset version.

Publish only after validation and completeness checks, with counts reconciling accepted/duplicate/rejected/excluded data. Validate the explicit output root and containment; an existing matching version is verified/reused, not overwritten. Conflicting/tampered/incomplete output and interrupted writes fail safely without a successful manifest or damage to an existing version. Temporary staging/atomic publication, cleanup limits and path/symlink/concurrent-run behavior must be specified and tested in the detailed plan. Never recursively delete a broad or unresolved directory.

### Real-data admission and completion gate

Research mode requires a named owner/source, documented license or permission, approved privacy/retention/access rules, source and mapping versions, observed coverage/units/timezone/availability limitations and a reviewed quality/admission report. None is established by synthetic operational records or passing tests. A real-data admission report may reject an unfit dataset honestly; it must not claim a usable research dataset was produced.

Do not invent a numerical minimum history, forecast horizon or accuracy threshold before examining admitted coverage and the intended downstream protocol. Report series lengths, gaps, censoring, quality exclusions and suitability/limitations; M6 freezes forecast/evaluation criteria against that evidence.
