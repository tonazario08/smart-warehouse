### Frozen candidate protocol for review

Use a single series per research run; reject mixing targets, units or reporting scopes. Research config forecast-protocol/1 pins train=[2020-01-01,2021-01-01), validation=[2021-01-01,2022-01-01), final_holdout=[2022-01-01,2023-01-01), horizons=(1,7), history_days=28 and imputation=none. Preserve M5's calendar masks and complete-window counts. Operational protocol must instead name source-supported dates/cutoffs and approved horizons before fitting; no default dates are invented from company research data.

For each origin o and horizon h, history is o-27 through o and target dates are o+1 through o+h. All history and all targets must be eligible to enter evaluation; targets lie wholly in their partition. In research mode, values from earlier dates in the final-vintage source are allowed as retrospective history; this explicitly does not prove historical availability. Operational history additionally requires available_at <= the origin's declared business-day cutoff. Do not silently apply the research waiver to operational mode.

Baselines: persistence predicts y[o] for every lead; seasonal_naive predicts y[o+k-7] for lead k=1..h. Both use exactly the same origins/targets as XGBoost. XGBoost uses a separate direct model for each lead. Features, in exact order, are y[o], y[o-1], ... y[o-27], mean of the last seven days, mean of the last 28 days, target-date ISO weekday (1..7) and target-date month (1..12). Calendar values are known at origin. No target-day actual, realized intermediate target, source percent-change field, current stock, scaling, encoding fit or imputation enters features.

Use native xgboost.train/DMatrix rather than adding scikit-learn. Proposed optional forecasting dependencies in pyproject.toml are xgboost==3.4.1, numpy==2.5.4 and scipy==1.18.1. PyPI metadata checked 2026-10-28 lists Python >=3.12 and Windows AMD64 wheels for all three; SciPy's declared NumPy range includes the proposed pin. This is metadata feasibility, not installation/runtime/security verification. A fresh isolated environment must resolve/install/test the pins before any experiment; do not reuse or upgrade the M4/M5 verification environment. Abort for a dependency incompatibility and report it rather than silently substituting versions.

Candidate order is max_depth=2 then max_depth=3. Both use booster=gbtree, objective=reg:squarederror, tree_method=hist, device=cpu, eta=0.05, min_child_weight=1, subsample=1, colsample_bytree=1, lambda=1, alpha=0, seed=42, nthread=1, verbosity=0 and num_boost_round=100. Set DMatrix nthread=1 as well; no GPU, distributed tuning or early stopping. Fit candidates on 2020 windows only; choose one candidate per horizon by validation point MAE, with exact ties resolved by candidate order. Freeze selection.json before any model holdout metrics. Refit the selected candidate on the union of eligible 2020 and 2021 partition windows, never a window straddling their boundary; evaluate once on 2022 origins. No training/tuning operation consumes holdout labels. Pre-origin 2022 history is allowed for later rolling origins; model parameters remain fixed.

Predictions are finite real units, not rounded integers. Clip negatives to zero consistently before scoring and record clip counts; nonfinite output fails the run. Metrics for each algorithm/horizon are point MAE=sum(abs(error))/N and WAPE=sum(abs(error))/sum(actual), stored as a ratio. When sum(actual)=0, WAPE=null with ZERO_ACTUAL_TOTAL; when N=0, both metrics are null with NO_ELIGIBLE_WINDOWS. Also report MAE of per-origin horizon totals, counts, exclusions and per-series results. Aggregate MAE/WAPE use pooled point sums/counts, never an unweighted average of ratios; do not combine different units or horizons. Overlapping horizon windows are disclosed and not treated as independent observations. Report all three algorithms; choosing XGBoost for the study does not imply it is the best operational model.

### Contracts, persistence and failure behavior

All new Python contracts use strict Pydantic fields and extra=forbid. ForecastConfig has schema_version=forecast-config/1, mode=research|operational, dataset_class=research|fixture copied from verified admission, data_version, protocol, feature_version=lag-calendar/1, candidate parameters above and target/scope/unit discriminators. Fixture admission is a separate explicit CLI opt-in, not a way to override source classification; matching research/operational mode still enforces its target/scope rules. ForecastWindow contains series_key, origin, history_dates/history_values, target_dates and target_values; only the training/evaluation layer holds target_values. PredictionRow contains series_key, origin, target_date, lead, horizon, algorithm=persistence|seasonal_naive|xgboost, finite nonnegative prediction and nullable actual. Operational future predictions have actual=null.

SelectionManifest binds data/config/feature/software hashes, per-horizon selection, training window hashes and validation metrics. ForecastRunManifest uses schema_version=forecast-run/1, run_id=frv1-<sha256>, run_kind=evaluation|forecast, mode, dataset_class, data_version, target, reporting_scope, unit, protocol, selection hash, software/package identity, trained_through (last actual training-label date), training_information_cutoff (aware UTC), knowledge_time_mode, business_timezone (IANA string for operational, null for publisher civil-date research), origin range, horizons, limitations and artifact hashes. Research retains retrospective_final_vintage, unknown source timezone and its actual admission knowledge bound; trained_through is not evidence that the final-vintage source was historically available. Research runs have no product_id/warehouse_id. Operational forecasts carry the verified binding and historical_as_of mode. Generation time is UTC execution metadata, not a training cutoff or a semantic-ID input. New attempts receive a separate immutable UTC receipt; reuse returns the original semantic run rather than rewriting timestamps.

The forecast command does not silently load the train-only candidate models from the selection stage as final models. It verifies selection/data/config identity, refits the frozen selected configuration using only eligible windows from the declared train and validation partitions, and saves those actual refitted models in the forecast run. It never adds holdout targets or refits on undeclared newer data. Record the refit window hash and trained_through, require trained_through <= origin and, for operational mode, training_information_cutoff <= the origin business-day cutoff with every training label available by that information cutoff. For all modes, model selection must itself have occurred before the requested forecast origin in the evaluation protocol; reject earlier/backdated origins that overlap selection targets. Forecasting a new data version requires a new verified selection for that version, not an unreviewed model substitution. A future inference origin needs only 28 eligible pre-origin history values and known target calendar dates; it must not require future actual target values to exist. Freshness remains a separate read-time check.

Selection directories are fsv1-<sha256> containing selection.json, validation.json and native JSON models. Evaluation directories contain manifest.json, predictions.jsonl, metrics.json, models/*.json and receipt.json; forecasts contain manifest.json, predictions.jsonl, binding.json, models/*.json and receipt.json. Exact model-file count is sum of configured horizon leads; no pickle, joblib, arbitrary Python object or user-uploaded model is loaded. Semantic IDs bind configuration, data version, selection, source/software identity and semantic artifact hashes; receipt timestamps are excluded. Verify canonical ordering, bounds, filenames, model hashes and predictions/metrics correspondence before reuse or publication. Same pinned CPU environment must reproduce point values within absolute 1e-6 and relative 1e-9 tolerance; exact existing-run reuse is byte preserving. Different environments are distinct provenance, not a cross-platform bitwise guarantee.

Publish only by explicit offline CLI into a configured local catalog. Define a separate PublicRunManifest, schema_version=forecast-public-run/1, containing original run_id, source_manifest_sha256, public metadata fields (kind/mode/dataset_class/data_version/target/scope/unit/protocol/knowledge-time/timezone/training-cutoff/origins/horizons/generated_at/limitations), safe public summary counts, a sanitized binding when present and hashes for only the files actually served. Each catalog directory contains public-manifest.json and predictions.jsonl, plus metrics.json for evaluation or binding.json for operational forecasts. It contains no native model or full private manifest. PublicBinding includes product_id, warehouse_id, product_key, warehouse_key, unit, data_version, available_at, approved_at and binding_sha256; permission_ref and private owner/rights material are excluded. Neither source_manifest_sha256 nor binding_sha256 claims that the API can reconstruct a private file it does not hold; these fields are provenance references. Publication verifies the full private run/binding before producing the projection. The public projection hash is separately computed over canonical public metadata and served-file hashes, not compared to the private full-run digest as if the files were identical.

Repository.verify_catalog_run validates the public schema, strict field relationships, allowed exact public file set, public hashes, prediction/metric consistency and current entity/unit binding without importing XGBoost/NumPy or requiring absent model files. It does not call the full native-model artifact verifier or infer private ownership permission from a projection. Existing current-user and role checks remain the backend authority. An owner-controlled catalog is a trust boundary; hashes detect accidental modification, not malicious-author authenticity. Atomic staging, exclusive output lock, interruption cleanup confined to owned staging, no overwrite of conflicting bytes, reparse-point/symlink refusal and path containment are mandatory. Bound input/catalog to 1000 runs, 50000 prediction rows per run, 10000 calendar dates and 256 MiB per run. Oversize/unrecognized input fails safely; never silently truncate it into a successful run.

Failed offline jobs create no successful run directory. Under the owned output root, a separate UUID attempt receipt records only state=failed, safe error code, mode/dataset_class/reporting_scope from the validated config, config digest and UTC time; no raw exception, path, source record or credential. Failures before config validation are not publishable. Operator-published failed receipts may be returned by the status endpoint after the same scope authorization; they are never advertised as successful runs. File permissions and owner-controlled publication must be checked before serving.

CLI commands: tune --bundle PATH --config PATH --output-root PATH; evaluate --bundle PATH --selection-dir PATH --output-root PATH; forecast --bundle PATH --selection-dir PATH --binding PATH --origin YYYY-MM-DD --output-root PATH; verify --run-dir PATH; publish --run-dir PATH --catalog-root PATH. Each command rejects fixture input by default; tests explicitly pass --allow-fixture without changing dataset classification. Run with python -m app.forecasting.cli. No implicit database connection or environment source fallback. Exit codes: 0 success/reuse, 2 input/schema/integrity, 3 insufficient or unadmitted input, 4 output conflict, 5 safe I/O failure, 6 fitting/prediction failure. stdout is a bounded structured summary of IDs/counts/status only; stderr uses safe codes. The catalog publisher additionally accepts a validated failed-attempt receipt through publish-failure --attempt PATH --catalog-root PATH.

### Proposed read API and permissions

Add Permission.FORECAST_READ (forecast:read) for admin/warehouse and Permission.FORECAST_RESEARCH_READ (forecast:research:read) for admin only, with matching frontend visibility helpers. Existing grants stay unchanged. Client has neither permission; no client research publication is proposed. Authenticate before catalog lookup. Research-mode data is never returned to warehouse users, including through guessed IDs, status counts or errors. Fixture-class data is rejected by default for every user; an isolated test/integration server may explicitly opt in, then applies the same research-versus-operational scope grants and mandatory fixture labeling. An inaccessible well-formed run ID returns the same 404 as an unknown ID; missing/invalid authentication remains 401, denied endpoint scope is 403, malformed identifiers/query values are 422.

| --- | --- |

Returns state=ready|unavailable|failed and a safe reason_code, newest authorized successful run summary or null and latest authorized failure code or null.
